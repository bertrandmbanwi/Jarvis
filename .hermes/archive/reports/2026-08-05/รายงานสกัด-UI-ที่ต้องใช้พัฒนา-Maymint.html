0. สรุปก่อน: UI ที่ Maymint ต้องมีจริง

คำตอบสั้น: ถ้าจะพัฒนา Maymint ให้ใช้จริง ไม่ใช่แค่เท่ ต้องมี 8 หน้าหรือ component หลัก: App Shell, Overlay, Command Bar, Progress Monitor, Stop/Cancel Controls, Confirmation Center, Mode Switcher, Memory Dashboard และ Settings/Provider Panel

UIเอาไว้ทำอะไรสถานะใน JarvisMaymint ควรทำยังไง
App Shellโครงหลัก มี mode tabs, connection, cost/statusมีใน StatusBar/Pageต้องมี แต่ปรับเป็น Maymint ไทย
Desktop Overlayร่างบนจอ: ฟัง/คิด/พูด/รออนุมัติมี OverlayView + Swift overlayทำก่อน
Command Barพิมพ์/พูดสั่งงานเร็วมี ChatInputต้องต่อ Hermes
Progress Monitorบอกงานถึงไหนมี PlanProgressขยายมากกว่า Jarvis
Stop/Cancelหยุดเสียง/งาน/agentมี stop_audio เฉพาะเสียงต้องเพิ่ม cancel งานจริง
Confirmation UXถามก่อนทำเรื่องเสี่ยงมี ConfirmationModalต้องแปลไทย + เพิ่ม detail
Mode Switchเลือกบุคลิก/โหมดงานมี view tabs แต่ไม่ใช่ working modesต้องออกแบบใหม่
Memory Dashboardดู/แก้สิ่งที่มายจำมีแค่นับ memory entriesต้องสร้างใหม่

1. UI Inventory จาก Jarvis ที่อ่านแล้ว

  • src/app/page.tsx — main shell รวม StatusBar, Cinematic, Chat, Dashboard, Product, PlanProgress, ConfirmationModal, SettingsPanel
  • StatusBar.tsx — mode tabs: Voice / Chat / System / Flows + connection + session cost
  • OverlayView.tsx และ desktop-overlay/JarvisOverlay.swift — overlay local WebSocket + hotkey + orb state
  • ChatInput.tsx — text input + mic button + send button
  • useVoiceRecorder.ts — browser mic recording, silence detection, upload to /voice/transcribe
  • useJarvisWebSocket.ts — WS event handler: streaming, audio, plan_progress, confirmation_required, stop_audio
  • PlanProgress.tsx — floating progress card, collapsed mini progress, subtask status
  • ConfirmationModal.tsx — risk modal approve/deny
  • DashboardView.tsx — activity log, system, memory count, costs, providers, product bets
  • SettingsPanel.tsx — API/model/voice/cost settings

สรุป: Jarvis มี UI หลายชิ้นที่ดี แต่หลายชิ้นยังเป็น “display” ไม่ใช่ “control UX” เต็ม เช่น memory ยังแค่นับจำนวน, cancel ยังหยุดเสียงไม่หยุดงาน, mode เป็น view mode ไม่ใช่ behavior mode

2. App Shell: โครงหน้าหลักของ Maymint

App Shell คือ “บ้าน” ของ Maymint บนจอใหญ่ ไม่ใช่ overlay ลอยเล็ก ๆ อย่างเดียว

ต้องมีอะไรบ้าง

  • Connection status: online / reconnecting / offline / error
  • Current provider/model: OpenRouter, Hermes provider, local fallback
  • Current Maymint mode: companion / secretary / builder / researcher / voice-short
  • Global controls: stop speaking, cancel current task, open overlay, open memory
  • Notification badge: pending confirmation, failed task, completed report
  • Keyboard shortcuts: command palette, push-to-talk, stop, open dashboard

3. Desktop Overlay / Presence UI

นี่คือ “ตัวมายบนจอ” ต้องเบา ไม่วุ่นวาย และสื่อสาร state ได้ใน 1 วินาที

Stateสี/อาการข้อความAction ที่ควรมี
Idleนุ่ม เงียบ ไม่รบกวนพร้อมค่ะคลิก = command palette
Listeningpulse ตามไมค์ฟังอยู่...หยุดฟัง
Thinkingหมุน/แสงช้ากำลังคิดยกเลิก
Workingprogress ringกำลังทำขั้นตอน 2/5ดูรายละเอียด / ยกเลิก
Speakingขยับตามเสียงกำลังพูดหยุดพูด
Need Confirmเหลือง/ส้มขออนุมัติอนุมัติ / ปฏิเสธ
Errorแดงนุ่มติดปัญหาดู error / retry

สิ่งที่ต้องระวัง

  • อย่าให้ overlay เปิด browser/หน้าต่างเยอะเอง
  • ต้องมีปุ่มซ่อน/ปิด/ย้ายตำแหน่ง
  • ต้องจำตำแหน่งหน้าต่าง
  • ต้องมี compact mode และ expanded mode
  • ต้องไม่แย่ง focus เวลาบอสทำงาน

4. Command UI: กล่องสั่งงานของบอส

Command UI ต้องรองรับทั้งพิมพ์และเสียง โดยเข้าใจภาษาไทยสไตล์บอส

พิมพ์/พูด→intent preview→เลือก mode/risk→ส่งเข้า Hermes→แสดง progress
Elementต้องมีเหตุผล
Input fieldplaceholder ไทย เช่น “สั่งมาย...”ลด friction
Mic buttonstate recording/transcribing/errorรู้ว่าฟังอยู่ไหม
Intent previewมายจะ: “ทำรายงาน HTML”กันเข้าใจผิด
Mode chipเลขา / นักวิจัย / นักสร้าง / เสียงสั้นสั่ง behavior
Risk hintอ่านอย่างเดียว / จะเขียนไฟล์ / จะรันคำสั่งช่วย safety
Recent commandsคำสั่งประจำของบอสเร็วขึ้น

5. Progress UI: การมองเห็นความคืบหน้า

Jarvis มี PlanProgress ที่ดี: progress bar, subtasks, running/completed/failed/skipped, collapsed mini card. แต่ Maymint ต้องละเอียดกว่าเพราะบอสใช้ agent ทำงานจริง

Progress ที่ควรแสดง

ระดับตัวอย่างUI
Taskทำรายงาน UI extractionชื่อ task + percent + elapsed time
Stepอ่าน component filesรายการ step พร้อม status
Toolread_file / terminal / browserแสดง tool แบบเข้าใจง่าย ไม่ dump output ยาว
Evidenceไฟล์/route ที่เจอคลิกดูหลักฐาน
Errorcommand failederror card + retry/skip/ask boss
ArtifactHTML report createdปุ่มเปิดไฟล์

ปัญหาที่ต้องกันไว้

  • งานบางอย่างไม่มี percent จริง → ใช้ step count แทน
  • tool output ยาวมาก → UI ต้อง summarize ไม่ยัดทั้งหมด
  • งาน background/cron/delegation ต้องมี task id และ resume state
  • ถ้าปิดหน้าต่างแล้วเปิดใหม่ ต้อง recover progress จาก session/task store

6. Stop / Cancel UI

Jarvis มี stopAudio() ส่ง stop_audio และหยุด local playback แต่ยังไม่พอสำหรับ Maymint เพราะบอสต้องหยุด “งาน” ด้วย ไม่ใช่แค่เสียง

ปุ่มหยุดอะไรต้องทำกับ backendUX หลังหยุด
หยุดพูดTTS/audiostop_audiostate กลับ idle/follow-up
หยุดฟังmic recordingclose stream / discard audioไม่ส่ง STT
ยกเลิกงานนี้current task/process/delegationcancel task idบอกว่ายกเลิกแล้ว
Pauseหยุดก่อนแต่ยังจำ contextpause/resume tokenปุ่ม resume
Emergency stopvoice+tools+desktop controlkill active processes / lock toolsต้อง confirm ว่าหยุดหมด

สำคัญ: ต้องแยก “หยุดพูด” กับ “ยกเลิกงาน” ไม่งั้นบอสกดหยุดเสียงแต่งานยังรันต่อโดยไม่รู้ตัว

7. Confirmation UX: ประสบการณ์ยืนยัน

Jarvis มี modal approve/deny แต่ Maymint ต้องละเอียดกว่า โดยเฉพาะถ้าจะคุม desktop/browser/file

ข้อมูลที่ modal ต้องบอก
  • มายจะทำอะไร แบบภาษาคน
  • tool/action ที่จะใช้
  • ไฟล์/เว็บ/app ที่กระทบ
  • risk level
  • ผลเสียถ้าพลาด
  • มีทางเลือกที่ปลอดภัยกว่าไหม
ปุ่มที่ควรมี
อนุมัติครั้งนี้ปฏิเสธดูรายละเอียดdry-runจำ allowlistหยุดทั้งหมด

ระดับความเสี่ยงที่ UI ต้องแสดง

Riskตัวอย่างDefault
Lowอ่านไฟล์, เปิดรายงานทำได้แต่ log
Mediumเขียนไฟล์ใน projectถามครั้งแรก/สรุป diff
Highคุม browser, ส่งข้อความ, แก้ไฟล์สำคัญต้อง confirm
Criticalshell destructive, credentials, payment, public postต้อง confirm + typed phrase หรือ manual

8. Mode Switch: สวิตช์โหมด

Jarvis มี view mode: Voice/Chat/System/Flows แต่นั่นคือ “หน้า” ไม่ใช่ “โหมดนิสัยการทำงาน” ของ Maymint

Maymint ModeพฤติกรรมUI ที่ต้องเปลี่ยน
Companionคุยเล่น อบอุ่น สั้นsoft overlay, no tool aggression
Secretaryจัดตาราง/เตือน/สรุปagenda, reminders, inbox
Researchชำแหละ/รายงาน/source evidenceevidence panel, report button
Buildercode/build/testterminal/test/progress focus
Voice Shortตอบเสียงสั้น รายละเอียดส่งเป็น text/htmlshort answer toggle
Safe Inspectอ่านก่อน ไม่รัน ไม่แก้read-only badge
Deep Workงานยาว/agents/cronbackground task monitor

ปัญหาที่ต้องกัน: อย่าให้ mode เป็นแค่สี UI ต้องส่งผลกับ system prompt/tool policy/response length/confirmation policy จริง

9. Memory Dashboard: แดชบอร์ดหน่วยความจำ

Jarvis dashboard แสดงแค่ memory count. สำหรับ Maymint ต้องเป็นหน้าให้บอส “เห็นและควบคุมความจำ”

หมวดตัวอย่างAction
Profileบอสชอบรายงาน HTML ภาษาไทยแก้ / lock / remove
ProjectsMaymint, Boss Library, voice overlayเปิด project / ดูล่าสุด
Command Dictionary“ชำแหละ” = reverse engineeringเพิ่มคำสั่ง / ทดสอบ intent
Preferencesตอบไทยสั้น, อย่ารันมั่วpin / unpin
Secrets Awarenessรู้ว่ามี key แต่ไม่โชว์ค่าrotate reminder / never reveal
Stale Memoryสิ่งที่อาจเก่าreview / archive

UI ที่ควรมี

  • search memory
  • filter by type: preference/project/person/procedure
  • diff before save
  • source link ว่าความจำมาจาก session ไหน
  • ปุ่ม “มายจำผิด”
  • ปุ่ม “อย่าจำเรื่องนี้อีก”
  • export เป็น Boss Library

13. ปัญหาที่จะเจอทีหลัง ถ้าไม่สกัด UI ให้ละเอียด

ปัญหาจะเกิดเมื่อกันยังไง
ปุ่มหยุดไม่หยุดงานจริงมีแค่ stop audioแยก cancel task/process/delegation
overlay state เพี้ยนvoice, chat, background task set state พร้อมกันcentral state machine
confirmation กวนเกินไปถามทุก actionrisk policy + allowlist + remember choice
confirmation น้อยเกินไปtools เสี่ยงไม่ถามdefault fail-closed สำหรับ high/critical
memory กลายเป็นกล่องดำจำเยอะ แต่บอสไม่เห็นmemory dashboard + source + edit
mode switch เป็นของปลอมเปลี่ยนแค่หน้า ไม่เปลี่ยน behaviormode ต้องผูก policy/model/response/tool risk
progress หลอกไม่มี stepจริง ใช้ spinner ยาวtask event schema บังคับทุกงานยาว
เสียงรำคาญTTS อ่านยาว/หยุดไม่ได้voice-short default + stop button

14. MVP Plan: ลำดับทำจริงที่มายแนะนำ

  1. Maymint Overlay v0: หน้าต่างลอย + state mock + hotkey + close/move/reset
  2. State Bridge: Hermes local event server ส่ง idle/thinking/working/speaking/error
  3. Progress Monitor: task_id + steps + active tool + artifact buttons
  4. Stop/Cancel Controls: stop audio, stop mic, cancel task, emergency stop
  5. Confirmation Center: Thai modal + risk + target + diff + approve/deny
  6. Command Bar: text command + recent commands + intent preview
  7. Mode Switch: behavior modes ที่ผูก policy จริง
  8. Push-to-talk Voice: mic → STT → Hermes → short TTS
  9. Memory Dashboard: view/search/edit/source/pin/archive
  10. Wake Word: ทำหลังสุดเมื่อ UX และ stop/cancel เสถียร

เหตุผลของลำดับนี้: ทำของที่เห็นภาพและควบคุมความเสี่ยงก่อน แล้วค่อยเพิ่มเสียง/desktop control ทีหลัง

15. Checklist ก่อนเริ่มพัฒนา Maymint UI

  • กำหนด state machine กลางก่อนเขียน overlay
  • กำหนด event schema ก่อนเขียน component
  • แยก stop speaking / stop mic / cancel task / emergency stop
  • ทุก long task ต้องมี task_id
  • ทุก high-risk action ต้องมี confirmation object
  • Memory ทุกชิ้นต้องมี source และปุ่มแก้/ลบ
  • Mode switch ต้องเปลี่ยน behavior จริง ไม่ใช่แค่ tab
  • Overlay ต้องมี compact/expanded/off และ reset position
  • Voice ต้อง default เป็น short answer
  • ห้ามโชว์ secrets ใน UI
  • ต้องมี sandbox/read-only mode สำหรับทดลอง desktop/browser control
  • ต้องมี browser/console verification ทุกครั้งที่แก้ HTML/UI
รายงานนี้เป็น HTML ภาษาไทย สกัดจาก Jarvis UI เพื่อใช้เป็น spec ก่อนพัฒนา Maymint ต่อ ไม่มี secrets และไม่ได้รัน full Jarvis
